Existing Scheduler Understanding (Checkpoint)

1. Where is the round robin scheduling decision made? Identify the relevant function and code region.

The round robin scheduling decision is made in the kernel's process management file (proc.c), in the scheduler() function. Each CPU runs scheduler() in an infinite loop. On each pass it acquires ptable.lock and runs a for loop over the process table (for(p = ptable.proc; p < &ptable.proc[NPROC]; p++)). Every process found in the RUNNABLE state is switched to, in process-table slot order, and when the end of the table is reached the scan starts over from the first slot. Round robin behavior comes from this repeated linear scan combined with the timer interrupt, which calls yield() so that a running process gives up the CPU after one time slice. This for loop is the region that will be replaced with the lottery selection.

2. What condition must hold before a process can be selected to run?

The process must be in the RUNNABLE state (p->state == RUNNABLE), and the scheduler must be holding ptable.lock while it checks. Processes that are UNUSED, EMBRYO, SLEEPING, RUNNING or ZOMBIE are skipped.

3. What important process-state or context changes occur when the scheduler transfers control to a process and when control returns to the scheduler?

When the scheduler transfers control to a process:
- The scheduler sets the per-CPU variable proc to the chosen process (proc = p).
- switchuvm(p) loads the process's page table and task state segment (kernel stack) so the CPU runs in that process's address space.
- The process state changes from RUNNABLE to RUNNING.
- swtch(&cpu->scheduler, proc->context) saves the scheduler's own context into cpu->scheduler and loads the chosen process's saved kernel context, so execution continues inside that process (in sched(), or in forkret() for a brand new process).
- ptable.lock stays held across the switch; the process is responsible for releasing it (e.g. in forkret) and reacquiring it before switching back.

When control returns to the scheduler:
- The process itself, not the scheduler, changes its own state before it calls sched(): yield() sets it to RUNNABLE (time slice ended), sleep() sets it to SLEEPING, and exit() sets it to ZOMBIE. The state is therefore not always RUNNABLE on return.
- The process calls sched(), which does swtch(&proc->context, cpu->scheduler). This saves the process's context and restores the scheduler's saved context, so the scheduler resumes right after its swtch call.
- The scheduler then calls switchkvm() to go back to the kernel-only page table and sets proc = 0, since no process is running on this CPU. ptable.lock is still held and the scheduler continues scanning.

Design Before Implementation (Checkpoint)

1. Where will the number of tickets for each process be stored?

In the process control block, struct proc in proc.h. I will add a new field (int tickets) holding the number of lottery tickets for that process. Because it lives in struct proc, it is stored per process-table slot and is directly accessible to settickets(), fork(), scheduler() and getpinfo().

2. Where will the default ticket value be initialized?

In allocproc() in proc.c, which sets tickets = 1 when it takes an UNUSED slot and marks it EMBRYO. I chose allocproc() rather than fork() because every process is created through allocproc(), including the first process created by userinit(), which never calls fork(). Initializing it in fork() alone would leave init with 0 tickets. allocproc() will also reset the ticks counter to 0 so a reused slot does not carry over old statistics.

3. How will a child process inherit the ticket count of its parent?

In fork(), after allocproc() has returned the new process (with the default of 1 ticket) and the other state has been copied from the parent, I will set np->tickets = proc->tickets, where proc is the calling (parent) process. This overrides the default, so a parent with 10 tickets produces a child that begins with 10 tickets.

4. How will your scheduler determine the total number of tickets held by RUNNABLE processes?

Each time through the scheduler loop, while holding ptable.lock, scheduler() will loop over every slot in ptable.proc and add p->tickets to a running total for each process whose state is RUNNABLE. Processes in any other state are not counted. If the total is 0 (no RUNNABLE processes), no lottery is held; the scheduler releases the lock and loops again.

5. How will a lottery winner be selected from the RUNNABLE processes?

I will implement a simple pseudo-random number generator inside the kernel (for example a linear congruential generator or xorshift with a static seed), since the user-level random functions are not available. The scheduler draws a random number and reduces it to the range 0..total_tickets-1 (winner = rand() % total). It then walks the process table again, keeping a running sum of the tickets of the RUNNABLE processes it passes. The first process for which the running sum becomes greater than the winning number (running sum > winner) is the winner and is switched to for that time slice. In effect, each RUNNABLE process owns the next block of numbers equal to its ticket count (the first owns 0..t1-1, the next t1..t1+t2-1, and so on). A process with more tickets covers a larger part of the 0..total-1 range, so its probability of winning is proportional to its share of the tickets.

6. Where and when will you maintain the tick count reported by getpinfo()?

The tick count will be a new field (int ticks) in struct proc, set to 0 in allocproc(). It is incremented in scheduler() each time a process is chosen as the lottery winner, right before switching to it (p->ticks++, while ptable.lock is held). That way it increases exactly once per time slice in which the process is selected to run, as the spec requires. getpinfo() will acquire ptable.lock and copy inuse (state != UNUSED), tickets, pid and ticks for each slot into the struct pstat, after validating the user pointer (argptr, returning -1 for a NULL or bad pointer).


Experimental Evaluation: expected CPU shares, observed results, and interpretation

Setup

The experiment program is xv6/user/lotterytest.c. The parent forks three CPU-bound children with 30, 20 and 10 tickets (a 3:2:1 ratio). The parent calls settickets() with the child's count right before each fork(), so each child inherits its intended tickets from the moment it is created. Each child then spins in an infinite loop that never sleeps or does I/O, so every time slice it wins is fully used. The parent sleeps for 100 timer ticks, calls getpinfo(), prints the accumulated ticks of the three children, and repeats this 30 times (3000 timer ticks in total). xv6 runs on one CPU (CPUS := 1). The plot of the results is in graph.pdf: panel (a) shows the accumulated ticks of each process over time and panel (b) shows each process's share of the three processes' ticks over time, with dashed lines at the expected values.

1. Prediction (made before running the experiment)

The lottery only counts RUNNABLE processes, and the other processes in the system (init, sh, and the parent between samples) spend almost all their time sleeping, so the three children are effectively the only processes in the lottery. Each time slice, a process wins with probability (its tickets) / (total tickets) = tickets / 60. The expected long-run CPU shares are therefore:

  30 tickets: 30/60 = 50.0%
  20 tickets: 20/60 = 33.3%
  10 tickets: 10/60 = 16.7%

Over 3000 time slices this predicts about 1500, 1000 and 500 ticks. I also predicted that the shares would be noticeably off early in the run, when only a few hundred lotteries have been held, and would move closer to these values the longer the processes run.

2. Results and comparison with the expected proportions

Shares of the three children's ticks at selected sample points (percent; expected 50.0 / 33.3 / 16.7):

  time   ticks (30/20/10)    30 tickets   20 tickets   10 tickets
   100     55 /   36 /   9     55.0         36.0          9.0
   300    152 /  110 /  38     50.7         36.7         12.7
   500    249 /  181 /  70     49.8         36.2         14.0
  1000    490 /  363 / 147     49.0         36.3         14.7
  2000    994 /  690 / 316     49.7         34.5         15.8
  3000   1493 / 1002 / 505     49.8         33.4         16.8

At the end of the run the processes received 1493, 1002 and 505 ticks, or 49.8%, 33.4% and 16.8% of the CPU. Every share is within 0.2 percentage points of the expected value, and the observed ratio is 2.96 : 1.98 : 1, very close to 3 : 2 : 1. (lotterytest itself printed 49.7% for the first process because it truncates instead of rounding.) The three children's ticks add up to the elapsed time at every sample (for example 1493 + 1002 + 505 = 3000 at time 3000), so the sleeping processes took a negligible share of the CPU, as assumed in the prediction.

Early in the run the shares were further off. After the first 100 ticks the 10-ticket process had only 9.0% instead of 16.7% (7.7 points low), and the 30-ticket process had 55.0%. The 20-ticket process was above its expected share at every sample, around 36-37% from time 300 to 1000, and only came down to 33.4% by the end of the run.

3. Why the observed proportions are not expected to be exact

- The scheduler is random. Every time slice is an independent lottery, so the number of slices a process wins out of n is a random (binomial) count, not a fixed fraction. A process with expected share p gets a share whose standard deviation is about sqrt(p(1-p)/n). After n = 100 slices this is about 5.0, 4.7 and 3.7 percentage points for the three processes, so deviations like the 7.7-point shortfall at time 100 are normal (about two standard deviations). After n = 3000 slices it is only about 0.9, 0.9 and 0.7 points, which matches the small final deviations. Lottery scheduling is only fair in a probabilistic sense: it gives the right proportions on average, not exactly.

- The samples are cumulative, so early luck lingers. A process that wins more than its share early (like the 20-ticket process here) keeps that surplus in its total, and it takes many later slices to dilute it. This is why the 20-ticket curve stayed above 33.3% for a long stretch even though each individual lottery was fair.

- The run is finite. Only 3000 lotteries were held; the exact proportions are only reached in the limit of infinitely many slices.

- ticks counts how many times a process was selected, not exact CPU time. A process selected part-way through a timer tick (for example right after the parent goes back to sleep) gets a shorter slice but still counts as one tick.

- Other processes interfere slightly. The parent wakes up every 100 ticks to call getpinfo() and print a line, and the shell and init exist in the background. They hold the CPU only briefly, but they are not part of the 3:2:1 split.

- The random numbers come from a pseudo-random generator (xorshift32) with a fixed seed. The sequence is evenly distributed but it is one particular deterministic sequence, so any single run shows one particular pattern of deviations rather than the exact average.

4. Do the observed proportions become more stable as the processes run longer?

Yes. Panel (b) of graph.pdf shows the share lines swinging widely during the first few hundred ticks and then flattening onto the dashed expected lines. Measured numerically, the largest deviation from the expected share at any of the first five samples (time 100 to 500) was 7.7 percentage points, while at every one of the last ten samples (time 2100 to 3000) it was at most 1.0 point. This matches the law of large numbers: the expected error shrinks in proportion to 1/sqrt(n), so running 30 times longer (from 100 to 3000 slices) should make the error about sqrt(30), or roughly 5.5 times, smaller, which is what the data shows (from about 5 points to under 1 point).

What becomes stable is the long-run cumulative share, not the short-term behavior. Within each individual 100-tick interval the shares kept fluctuating for the whole run (the 30-ticket process got between 42% and 58% of the slices in different intervals, and the 10-ticket process between 9% and 25%). The lottery does not get more precise over time; the random deviations simply average out as more slices accumulate. So lottery scheduling achieves proportional sharing well over long periods but gives weaker guarantees over short periods.

Additional Test Design

1. Property / failure mode to test

A process with only one ticket must still receive its fair share of the CPU (1/total of the time slices), no matter where it sits in the process table. In particular it must never be starved completely. The plausible failure mode is an off-by-one error in how the winning ticket is mapped to a process. The scheduler draws a number in [0, total) and walks the RUNNABLE processes with a running sum of tickets; the winner is the first process whose running sum is greater than the drawn number. Small mistakes here - drawing from [0, total - 1) or [1, total), comparing with >= instead of >, or starting the running sum at the wrong value - shift the boundary between two processes' ticket ranges by one ticket. For processes with thousands of tickets this changes their share by a fraction of a percent and is invisible, but a process with exactly one ticket at the beginning or end of the table loses its only ticket and is never scheduled (or the process next to it gets an extra ticket and double the expected share for a 1-ticket process).

2. Setup

A user program (for example onetickettest.c) forks three CPU-bound children that spin forever without sleeping:
  - child A with 1 ticket   (forked first, so it sits earliest in the process table)
  - child B with 98 tickets (forked second)
  - child C with 1 ticket   (forked last, so it sits latest in the process table)
for a total of 100 tickets. As in lotterytest, the parent calls settickets() with each child's count right before the fork() so the child holds the right number of tickets from the start. Placing a 1-ticket process at both ends of the table covers an off-by-one error in either direction. The parent then gives itself many tickets (so it can wake up promptly), sleeps for 2000 timer ticks, calls getpinfo(), records the ticks of A, B and C, kills the children and reports the result. xv6 runs on one CPU.

3. Expected behavior of a correct implementation

Each 1-ticket child should win about 1% of the 2000 lotteries: on average 20 ticks, with a standard deviation of about 4.5 ticks (binomial, n = 2000, p = 0.01). B should get about 98%, roughly 1960 ticks. The test passes if A and C each have between 5 and 40 ticks. For a correct scheduler the chance of falling below 5 is about 0.0016% and the chance of exceeding 40 is about 0.0023%, so a correct implementation essentially never fails this test.

4. Result that would indicate an incorrect implementation

- A or C has 0 ticks (or only a handful, below 5): the process is starved. For a correct scheduler the probability of 0 ticks in 2000 lotteries is 0.99^2000, about 2 in a billion, so this is a strong sign that the first or last ticket of the range can never be drawn.
- A or C has far more than 40 ticks: it is getting extra tickets' worth of probability, for example because a boundary ticket of its neighbour is mapped to it.
- B's ticks are not close to 98% of the total, or the three counts do not add up to roughly the elapsed time: the lottery is not covering the ticket range correctly.

5. Why this test adds useful coverage beyond the provided tests

The provided tests check ratios between processes with large differences in tickets (high_tickets requires the high process to get more than 20 times the ticks of the low one), equal sharing among many equal processes (stress_equal), and the error between one high and many low processes that each hold thousands of tickets (stress_manylow). None of them checks the exact share of a process holding a single ticket, and a starved 1-ticket process would still pass all of them - for example in high_tickets a low process with 0 ticks makes the "more than 20 times" check pass even more easily. Off-by-one errors at the edges of the ticket range are among the most likely bugs in a lottery scheduler, and they are only visible when a process's whole share is one ticket. This test isolates exactly that case, and it also confirms that the default of one ticket per process (which every ordinary process in the system has) actually gives a process a chance to run.

It also pointed out a second failure mode in my own scheduler: the ticket total is a 32-bit uint, so if the RUNNABLE processes' tickets add up to 2^32 or more (for example three processes with 2,000,000,000 tickets each) the total wraps around and the lottery picks the wrong winners.

3. How I verified it: I read the provided tests myself to confirm the coverage gap. I recomputed the statistics by hand: mean = 2000 x 0.01 = 20, standard deviation = sqrt(2000 x 0.01 x 0.99), about 4.45, and the chance of a correct 1-ticket process getting 0 ticks = 0.99^2000, about 2 x 10^-9. For the overflow, I checked the arithmetic: 3 x 2,000,000,000 = 6,000,000,000, which is larger than 2^32 = 4,294,967,296 and wraps to 1,705,032,704, so the first process (2,000,000,000 tickets) would win every lottery. None of the provided tests use more than 100,000,000 tickets per process, so this case is not reached by them. I chose the 1-ticket test for the report because it targets a bug the provided tests cannot detect without requiring kernel changes, and I decided not to implement it since implementation is optional.
