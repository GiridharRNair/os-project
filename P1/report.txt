Existing Scheduler Understanding

1. Where is the round robin scheduling decision made? Identify the relevant function and code region.

The round robin scheduling decision is made in the kernel's process management file (proc.c), in the scheduler() function. Each CPU runs scheduler() in an infinite loop. On each pass it acquires ptable.lock and runs a for loop over the process table (for(p = ptable.proc; p < &ptable.proc[NPROC]; p++)). Every process found in the RUNNABLE state is switched to, in process-table slot order, and when the end of the table is reached the scan starts over from the first slot. Round robin behavior comes from this repeated linear scan combined with the timer interrupt, which calls yield() so that a running process gives up the CPU after one time slice. This for loop is the region that will be replaced with the lottery selection.

2. What condition must hold before a process can be selected to run?

The process must be in the RUNNABLE state (p->state == RUNNABLE), and the scheduler must be holding ptable.lock while it checks. Processes that are UNUSED, EMBRYO, SLEEPING, RUNNING or ZOMBIE are skipped.

3. What important process-state or context changes occur when the scheduler transfers control to a process and when control returns to the scheduler?

When the scheduler transfers control to a process:
- The scheduler sets the per-CPU variable proc to the chosen process (proc = p).
- switchuvm(p) loads the process's page table and task state segment (kernel stack) so the CPU runs in that process's address space.
- The process state changes from RUNNABLE to RUNNING.
- swtch(&cpu->scheduler, proc->context) saves the scheduler's own context into cpu->scheduler and loads the chosen process's saved kernel context, so execution continues inside that process (in sched(), or in forkret() for a brand new process).
- ptable.lock stays held across the switch; the process is responsible for releasing it (e.g. in forkret) and reacquiring it before switching back.

When control returns to the scheduler:
- The process itself, not the scheduler, changes its own state before it calls sched(): yield() sets it to RUNNABLE (time slice ended), sleep() sets it to SLEEPING, and exit() sets it to ZOMBIE. The state is therefore not always RUNNABLE on return.
- The process calls sched(), which does swtch(&proc->context, cpu->scheduler). This saves the process's context and restores the scheduler's saved context, so the scheduler resumes right after its swtch call.
- The scheduler then calls switchkvm() to go back to the kernel-only page table and sets proc = 0, since no process is running on this CPU. ptable.lock is still held and the scheduler continues scanning.

Design Before Implementation

1. Where will the number of tickets for each process be stored?

In the process control block, struct proc in proc.h. I will add a new field (int tickets) holding the number of lottery tickets for that process. Because it lives in struct proc, it is stored per process-table slot and is directly accessible to settickets(), fork(), scheduler() and getpinfo().

2. Where will the default ticket value be initialized?

In allocproc() in proc.c, which sets tickets = 1 when it takes an UNUSED slot and marks it EMBRYO. I chose allocproc() rather than fork() because every process is created through allocproc(), including the first process created by userinit(), which never calls fork(). Initializing it in fork() alone would leave init with 0 tickets. allocproc() will also reset the ticks counter to 0 so a reused slot does not carry over old statistics.

3. How will a child process inherit the ticket count of its parent?

In fork(), after allocproc() has returned the new process (with the default of 1 ticket) and the other state has been copied from the parent, I will set np->tickets = proc->tickets, where proc is the calling (parent) process. This overrides the default, so a parent with 10 tickets produces a child that begins with 10 tickets.

4. How will your scheduler determine the total number of tickets held by RUNNABLE processes?

Each time through the scheduler loop, while holding ptable.lock, scheduler() will loop over every slot in ptable.proc and add p->tickets to a running total for each process whose state is RUNNABLE. Processes in any other state are not counted. If the total is 0 (no RUNNABLE processes), no lottery is held; the scheduler releases the lock and loops again.

5. How will a lottery winner be selected from the RUNNABLE processes?

I will implement a simple pseudo-random number generator inside the kernel (for example a linear congruential generator or xorshift with a static seed), since the user-level random functions are not available. The scheduler draws a random number and reduces it to the range 1..total_tickets (e.g. (rand() % total) + 1). It then walks the process table again, and for each RUNNABLE process subtracts that process's tickets from the number (or equivalently keeps a running sum of tickets). The first process for which the number reaches zero or below (running sum >= winning number) is the winner and is switched to for that time slice. A process with more tickets covers a larger part of the 1..total range, so its probability of winning is proportional to its share of the tickets.

6. Where and when will you maintain the tick count reported by getpinfo()?

The tick count will be a new field (int ticks) in struct proc, set to 0 in allocproc(). It is incremented in scheduler() each time a process is chosen as the lottery winner, right before switching to it (p->ticks++, while ptable.lock is held). That way it increases exactly once per time slice in which the process is selected to run, as the spec requires. getpinfo() will acquire ptable.lock and copy inuse (state != UNUSED), tickets, pid and ticks for each slot into the struct pstat, after validating the user pointer (argptr, returning -1 for a NULL or bad pointer).
